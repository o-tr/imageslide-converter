# EIA (Efficient Image Archive) バージョン1 仕様書

## 概要

本文書は、画像シーケンスの効率的な保存と送信のために設計されたバイナリコンテナフォーマットである EIA (Efficient Image Archive) バージョン1 フォーマットを定義します。EIA v1は、差分エンコーディングとLZ4圧縮により、フレーム間の差異が最小限の画像シーケンスに対して大幅な圧縮効果を提供します。

## 1. はじめに

### 1.1 目的

EIA v1フォーマットは、特にスライドプレゼンテーションやUIスクリーンショットのようなフレーム間の差異が最小限の画像シーケンスを効率的に保存するために設計されています。このフォーマットは以下の手法により圧縮を実現します：

- クロップ領域の差分エンコーディング
- 画像データのLZ4圧縮
- 高速アクセス向けの最適化されたバイナリ構造

### 1.2 用語

本文書における「しなければならない（MUST）」、「してはならない（MUST NOT）」、「要求される（REQUIRED）」、「するものとする（SHALL）」、「しないものとする（SHALL NOT）」、「すべきである（SHOULD）」、「すべきでない（SHOULD NOT）」、「推奨される（RECOMMENDED）」、「してもよい（MAY）」、「選択的（OPTIONAL）」は、RFC 2119に記載されているとおりに解釈されるものとします。

### 1.3 フォーマット識別子

EIA v1ファイルは以下により識別されます：
- タイプ識別子: `"eia"`
- バージョン番号: `1`
- 圧縮方式: `"lz4"`

## 2. ファイル構造

### 2.1 全体構造

EIA v1ファイルは以下で構成されます：

```
[ヘッダー][マニフェスト][データセクション]
```

具体的には：

```
EIA^{manifest_json}${compressed_block_0}{compressed_block_1}...
```

ヘッダーとマニフェストはUTF-8テキストとして格納され、`$` の直後から圧縮データが続きます。

### 2.2 ヘッダー形式

ファイルヘッダーは、リテラル文字列 `"EIA^"` で始まり、続いてJSONエンコードされたマニフェスト、そして `"$"` で終端されなければなりません（MUST）：

```
EIA^{manifest_json}$
```

ここで `{manifest_json}` は JSONエンコードされた EIAManifestV1 オブジェクトです。

マジックバイト列 `45 49 41 5E` (`EIA^`) を検証することでEIAファイルを識別できます。

### 2.3 データセクション

データセクションは `$` 終端文字の直後から始まります。すべての `s`（開始オフセット）フィールドは、**この `$` の直後のバイトを起点（オフセット0）とした圧縮済みバイト単位のオフセット**です。

```
...{manifest}$[byte 0][byte 1][byte 2]...
               ↑ ここが s=0
```

### 2.4 マニフェスト構造

マニフェストは以下の必須フィールドを持つJSONオブジェクトです：

```typescript
type EIAManifestV1 = {
  t: "eia";           // タイプ識別子（"eia"でなければならない）
  c: "lz4";           // 圧縮方式（"lz4"でなければならない）
  v: 1;               // バージョン番号（常に 1）
  f: string[];        // 機能配列
  e: EIAExtension[];  // 拡張配列
  i: EIAFileV1[];     // アイテム配列
  m?: EIASignageManifest; // オプションのサイネージマニフェスト
  ac?: EIAAnimationContainer; // オプションのアニメーションコンテナ
}
```

**バージョン番号:**
- `1`: EIA v1（現行で唯一の値）

`ac` フィールドを含むマニフェストも v1 互換の拡張として扱うため、`v` を bump する必要はありません。

#### 2.4.1 機能配列

機能配列（`f`）は使用中の各テクスチャフォーマットに対して `"Format:{format_name}"` 形式の文字列を含まなければなりません（MUST）。アニメーション機能を使用する場合は追加の識別子を含みます：

- `"Format:RGB24"` など：使用テクスチャフォーマット
- `"Feature:animation"`: `ac` フィールドを含む場合

#### 2.4.2 拡張配列

拡張配列（`e`）は、アイテムの拡張オブジェクトで使用されるすべての拡張キーを含まなければなりません（MUST）。現在サポートされている拡張：
- `"note"`: 個別アイテムのテキストアノテーション
- `"a"`: アニメーション参照配列

#### 2.4.3 アイテム配列

アイテム配列（`i`）は、アーカイブ内の各画像を記述する EIAFileV1 オブジェクトを含まなければなりません（MUST）。`i` 配列内のすべてのアイテムは、一意の `n`（名前/識別子）を持たなければなりません（MUST）。

## 3. ファイルタイプ

### 3.1 マスターファイル

マスターファイルは、依存関係のない完全な画像データを含みます：

```typescript
type EIAFileV1Master = {
  t: "m";             // タイプ（"m"でなければならない）
  n: string;          // 名前/識別子
  f: TTextureFormat;  // フォーマット識別子
  w: number;          // 幅（ピクセル）
  h: number;          // 高さ（ピクセル）
  s: number;          // データセクション内の圧縮ブロック開始オフセット（§2.3参照）
  l: number;          // LZ4圧縮後のバイト長
  u: number;          // LZ4展開後（非圧縮）のバイト長（= w × h × bytes_per_pixel）
  e?: EIAExtensionObject; // オプション拡張
}
```

`s` は `$` 直後を起点とした**圧縮済みバイト**単位のオフセットです。`l` バイト読み取り、LZ4展開すると `u` バイトの画像データが得られます。

### 3.2 クロップファイル

クロップファイルは、ベース画像を参照する差分データを含みます：

```typescript
type EIAFileV1Cropped = {
  t: "c";             // タイプ（"c"でなければならない）
  b: string;          // ベースファイルの名前（同一アーカイブ内のアイテムの `n` 値）
  n: string;          // 名前/識別子
  f: TTextureFormat;  // フォーマット識別子
  w: number;          // 元の幅（ピクセル）
  h: number;          // 元の高さ（ピクセル）
  s: number;          // データセクション内の圧縮ブロック開始オフセット（§2.3参照）
  l: number;          // LZ4圧縮後のバイト長
  u: number;          // LZ4展開後（非圧縮）のバイト長（= 全パーツの l の合計）
  e?: EIAExtensionObject; // オプション拡張
  r: EIAFileV1CroppedPart[]; // 矩形パーツ配列
}
```

`s` / `l` / `u` はマスターファイルと同じ意味です。`u` はすべてのパーツのピクセルデータを連結した非圧縮バイト長に等しくなります。`u` はすべてのパーツの `l` の合計に等しくなければなりません（MUST）。`EIAFileV1Cropped` の `f`、`w`、`h` は、ベースファイルの `f`、`w`、`h` と等しくなければなりません（MUST）。`EIAFileV1Cropped.b` の参照連鎖は循環を形成してはなりません（MUST NOT）。デコーダーは参照解決時に深さ制限を設けなければなりません（MUST）。

#### 3.2.1 クロップパーツ

各クロップパーツは、ベース画像と異なる矩形領域を記述します：

```typescript
type EIAFileV1CroppedPart = {
  x: number;  // ベース画像内のX座標（ピクセル、左上原点）
  y: number;  // ベース画像内のY座標（ピクセル、左上原点）
  w: number;  // 幅（ピクセル）
  h: number;  // 高さ（ピクセル）
  s: number;  // このファイルの非圧縮連結バッファ内のバイトオフセット（§4.3参照）
  l: number;  // このパーツの非圧縮ピクセルデータのバイト長（= w × h × bytes_per_pixel）
}
```

> **重要**: `EIAFileV1CroppedPart.s` の座標系は `EIAFileV1Cropped.s` とは異なります。
>
> - `EIAFileV1Cropped.s` — データセクション内の**圧縮済みバイト**オフセット
> - `EIAFileV1CroppedPart.s` — このファイルのLZ4**展開後バッファ**内のバイトオフセット
>
> 最初のパーツは常に `s = 0` であり、以降のパーツの `s` は先行するすべてのパーツの `l` の累積合計に等しいです。各パーツは以下を満たさなければなりません（MUST）：`x ≥ 0`、`y ≥ 0`、`w > 0`、`h > 0`、`x + w ≤ base.w`、`y + h ≤ base.h`。また、`s + l` はファイルの展開後バッファサイズ（`file.u`）を超えてはなりません（MUST）。各パーツの `l` は `w × h × bytes_per_pixel` に等しくなければなりません（MUST）。

## 4. データセクション

### 4.1 構造

データセクションは `$` 終端文字の直後に続き、各ファイルのLZ4圧縮済みブロックが配置されます。各ブロックは独立して圧縮・展開できます。

アニメーションコンテナ（`ac`）が存在する場合、スライドデータ（`i` 配列に対応するブロック）の後に、フレームプール（`ac.pool`）の圧縮ブロックが続きます。プールブロックは `pool` 配列のインデックス順（`pool[0]`, `pool[1]`, ...）に連続して配置されます。各プールブロックの `s` は、すべてのスライドデータブロックの合計圧縮バイト長以上でなければなりません（MUST）。

```text
[スライドデータブロック ...][アニメーションプールブロック ...]
```

### 4.2 圧縮

- すべての画像データはLZ4を使用して圧縮されなければなりません（MUST）
- 各ファイルおよび各プールフレームのデータは独立して圧縮されます
- クロップファイルは圧縮前にすべてのパーツのピクセルデータを順番に連結します

### 4.3 データレイアウト

#### マスターファイル

```
compressed_block:
  └─ LZ4展開 → 完全な画像データ（w × h × bytes_per_pixel バイト）
```

#### クロップファイル

```
compressed_block:
  └─ LZ4展開 → [part[0]のピクセルデータ][part[1]のピクセルデータ]...
                 ↑ s=0                    ↑ s=part[0].l

各パーツのピクセルデータ:
  - サイズ = w × h × bytes_per_pixel バイト
  - 上から下、左から右の行優先順
```

クロップファイルをデコードする手順：
1. `file.s` から `file.l` バイトを読み取る
2. LZ4展開して `file.u` バイトのバッファを得る
3. 各パーツ `r[i]` について、バッファ内の `r[i].s` から `r[i].l` バイトを読み取り、ベース画像の `(r[i].x, r[i].y)` から `r[i].w × r[i].h` の矩形領域に書き込む

#### アニメーションプールフレーム

アニメーションプールの各フレームは、スライドのマスター/クロップファイルと同じデータレイアウトを使用します。マスターフレームは完全な画像データ、クロップフレームは差分パーツデータです。

## 5. サポートされるフォーマット

### 5.1 テクスチャフォーマット

現在サポートされているテクスチャフォーマット：
- `"RGB24"`: 24ビットRGB（ピクセルあたり3バイト）
- `"RGBA32"`: 32ビットRGBA（ピクセルあたり4バイト）

### 5.2 フォーマット要件

- ピクセルデータは指定されたフォーマットで保存されなければなりません（MUST）
- RGB24フォーマットはRGB順で1チャンネルあたり8ビットを使用しなければなりません（MUST）
- RGBA32フォーマットはRGBA順で1チャンネルあたり8ビットを使用しなければなりません（MUST）

## 6. 拡張

### 6.1 拡張オブジェクト

拡張はアイテムのオプションの `e` フィールドに保存されます：

```typescript
type EIAExtensionObject = {
  note?: string;           // オプションテキストアノテーション（UTF-8）
  a?: EIAAnimationRef[];   // アニメーション参照配列（§7.4参照）
}
```

### 6.2 ノート拡張

`note` 拡張は画像のUTF-8エンコードされたテキストアノテーションを含んでもよいです（MAY）。

## 7. アニメーション拡張

アニメーション拡張により、スライド内にGIF等のアニメーションを配置できます。アニメーションのフレームデータはマニフェストのトップレベルに集約され、スライドはその配置情報のみを参照します。

### 7.1 アニメーションコンテナ

アニメーションフレームとその再生シーケンスは、アニメーションコンテナ（`ac`）に集約されます：

```typescript
type EIAAnimationContainer = {
  pool: EIAAnimFramePoolItem[]; // ユニークフレームのプール
  anims: EIAAnimation[];        // アニメーション（GIF）定義配列
}
```

`ac` が存在する場合、`manifest.f` に `"Feature:animation"` を含めなければなりません（MUST）。`ac` が存在する場合、`pool` と `anims` は空であってはなりません（MUST）。

### 7.2 フレームプール

フレームプールは、全アニメーションで使用されるユニークなフレームデータを格納します。エンコーダーは複数のアニメーションや同一アニメーション内の繰り返しフレーム（往復GIF等）で同一のフレームデータが存在する場合、単一のプールエントリを共有すべきです（SHOULD）。

```typescript
type EIAAnimFramePoolItem =
  | EIAAnimFramePoolItemMaster
  | EIAAnimFramePoolItemCropped;

type EIAAnimFramePoolItemMaster = {
  t: "m";            // タイプ（マスター）
  f: TTextureFormat; // テクスチャフォーマット
  w: number;         // フレーム幅（ピクセル）
  h: number;         // フレーム高さ（ピクセル）
  s: number;         // データセクション内の圧縮ブロック開始オフセット（§2.3と同じ座標系）
  l: number;         // LZ4圧縮後のバイト長
  u: number;         // LZ4展開後のバイト長（= w × h × bytes_per_pixel）
}

type EIAAnimFramePoolItemCropped = {
  t: "c";            // タイプ（クロップ）
  f: TTextureFormat; // テクスチャフォーマット
  w: number;         // フレーム幅（ピクセル）
  h: number;         // フレーム高さ（ピクセル）
  b: number;         // ベースフレームの pool 配列内インデックス
  s: number;         // データセクション内の圧縮ブロック開始オフセット（§2.3と同じ座標系）
  l: number;         // LZ4圧縮後のバイト長
  u: number;         // LZ4展開後のバイト長（= 全パーツの l の合計）
  r: EIAFileV1CroppedPart[]; // 変化した矩形パーツ配列
}
```

> **重要**: `EIAAnimFramePoolItemCropped.b` は、同一 `pool` 配列内の他のプールエントリを参照します。スライドのクロップファイル（`EIAFileV1Cropped.b`）とは異なり、ここでは**数値インデックス**（文字列ではなく）を使用します。
>
> 参照連鎖（参照先がさらに `t: "c"` であるケース）は許可されますが、エンコーダーは循環参照を生成してはなりません（MUST NOT）。デコーダーは参照を辿る際に深さ制限を設けなければなりません（MUST）。推奨される最大深度は 64 です。`b` は有効なプールインデックスでなければなりません（MUST）：`0 ≤ b < pool.length`。フレームは自身を参照してはなりません（MUST NOT）。`b` は自身より前のインデックスを参照する必要はありません。デコーダーは依存関係を解決してデコードしなければなりません（MUST）。例えば、未デコードのフレームを参照する場合は遅延デコード、メモ化付き再帰、またはトポロジカルソートを使用して、すべての依存関係が満たされた後にクロップ合成を行います。

`r` 内の `EIAFileV1CroppedPart.s` は、クロップファイルと同様に **LZ4展開後バッファ内のバイトオフセット**（最初のパーツは常に `s = 0`）です。`EIAAnimFramePoolItemCropped.s`（圧縮空間）とは座標系が異なります（§3.2.1の注意事項を参照）。`r` は空であってはなりません（MUST）。`r` 内の各パーツは以下を満たさなければなりません（MUST）：`x ≥ 0`、`y ≥ 0`、`w > 0`、`h > 0`、`x + w ≤ pool[b].w`、`y + h ≤ pool[b].h`、`s + l ≤ u`、`l == w × h × bytes_per_pixel`。なお、`EIAAnimFramePoolItemCropped` の `f`、`w`、`h` は、参照先のベースフレーム `pool[b]` の `f`、`w`、`h` と等しくなければなりません（MUST）。この自己記述フィールドにより、デコーダーは `b` 参照を辿らずにフレームの寸法とフォーマットを検証できます。また、`u` はすべてのパーツの `l` の合計に等しくなければなりません（MUST）。

### 7.3 アニメーション定義

アニメーション定義は1つのGIF等に相当し、フレームシーケンスと属性を記述します。表示サイズはスライド側の `EIAAnimationRef` で決定されるため、`EIAAnimation` は寸法を持ちません：

```typescript
type EIAAnimation = {
  id: string;   // 一意のアニメーション識別子
  fps: number;  // フレームレート
  seq: number[]; // フレームシーケンス（pool内インデックスの配列）
}
```

`seq` の各要素は `pool` 配列内のインデックスです。同一フレームデータを複数回参照することで、往復GIF等の繰り返しフレームをデータ重複なく表現できます。`seq` は空であってはなりません（MUST）。`seq` の各要素は有効なプールインデックスでなければなりません（MUST）：`0 ≤ seq[i] < pool.length`。すべてのインデックスフィールド（`seq[i]` および `EIAAnimFramePoolItemCropped.b`）は非負整数でなければなりません（MUST）。`seq` で参照されるすべてのフレームは、同じ `w`、`h`、`f` を持たなければなりません（MUST）。`fps` は正の有限値でなければなりません（MUST）：`fps > 0`。`ac.anims` 内のすべてのアニメーションは、一意かつ空でない `id` を持たなければなりません（MUST）。

### 7.4 スライドからのアニメーション参照

スライドは自身の拡張オブジェクト（`e.a`）にアニメーション参照配列を格納し、配置するアニメーションを指定します：

```typescript
// e.a はアニメーション参照の JSON 配列（JSON.stringify せず、そのまま格納）
type EIAAnimationRef = {
  id: string;  // ac.anims 内のアニメーション識別子
  x: number;   // ベース画像内のアニメーション表示領域X座標
  y: number;   // ベース画像内のアニメーション表示領域Y座標
  w: number;   // 表示幅（ピクセル）
  h: number;   // 表示高さ（ピクセル）
}
```

スライドから参照されたアニメーションは、そのスライドの表示位置（`x`, `y`）に配置されます。`e.a` が存在する場合、`manifest.ac` も存在しなければなりません（MUST）。複数のスライドが同じ `id` を参照してもよいです（MAY）。`id` は `ac.anims` 内に存在するアニメーション識別子でなければなりません（MUST）。各参照は以下を満たさなければなりません（MUST）：`x ≥ 0`、`y ≥ 0`、`w > 0`、`h > 0`、`x < slide.w`、`y < slide.h`。`x + w` または `y + h` がスライドの寸法を超える場合、デコーダーはスライド境界でクリップしなければなりません（MUST）。

### 7.5 アニメーションデコード手順

1. `manifest.ac` が存在する場合、`pool` 内の各フレームを必要に応じて依存関係を解決してデコードする
   - `t: "m"` はそのまま完全フレーム画像として使用する
   - `t: "c"` は `pool[b]` の画像データを**コピー**し、各パーツを適用して合成する。ベースフレームのバッファを直接変更してはならない（MUST NOT）
2. `seq` に従って、対応するプールフレームを時系列に並べる
3. `floor(Time.now * fps) % seq.length` でフレームインデックスを計算する。ここで `Time.now` は Unix エポックからの経過秒数とする。この計算によりアニメーションは無限に循環再生される。Unix エポックを基点とすることで、異なるデコーダー間で同一フレームが同時に表示され、サイネージ等の同期再生が可能になる
4. 選択されたフレーム画像を表示スロット（`EIAAnimationRef.x`, `EIAAnimationRef.y`, `EIAAnimationRef.w`, `EIAAnimationRef.h`）に配置する。フレームのピクセルサイズ（`pool[seq[i]].w`, `pool[seq[i]].h`）と表示サイズ（`EIAAnimationRef.w`, `EIAAnimationRef.h`）が異なる場合、デコーダーはフレームを表示サイズにスケールしなければなりません（MUST）

## 8. 処理ガイドライン

### 8.1 エンコーディング

エンコーダーは以下をすべきです（SHOULD）：
- 変化が最小限のシーケンスに差分エンコーディングを使用する
- 圧縮とランダムアクセスのバランスを取るためキーフレーム間隔を設定する
- 冗長データを最小化するため矩形配置を最適化する
- 複数のアニメーション間で同一のフレームデータを共有する
- アニメーションがスライドの領域外にはみ出す場合、はみ出した部分を切り落とし、スライドの境界内に収める

### 8.2 デコーディング

デコーダーは以下をしなければなりません（MUST）：
- 処理前にヘッダー形式（`EIA^` マジック）を検証する
- バージョン互換性をチェックする
- LZ4を使用してデータを展開する
- ベース画像にクロップパーツを適用して画像を再構築する
- `EIAFileV1Cropped.s`（圧縮空間オフセット）と `EIAFileV1CroppedPart.s`（展開後バッファオフセット）を区別して処理する
- `manifest.ac` が存在する場合、フレームプールを正しくデコードする
- フレームプール参照の循環を検出し防止する

### 8.3 エラーハンドリング

実装は以下を処理しなければなりません（MUST）：
- 無効なヘッダー形式
- サポートされていないバージョン
- 圧縮エラー
- 欠損ベースファイル参照
- 不正なプール参照インデックス
- 存在しないアニメーション識別子への参照
- `e.a` の存在するスライドで `manifest.ac` が欠落している場合
- フレームプール参照の循環
- クロップファイル参照の循環
- 圧縮空間のオフセット範囲外参照（`s + l` がデータセクションのバイト長を超える）
- 展開後バッファのオフセット範囲外参照（`part.s + part.l` が `file.u` を超える）
- パーツの `l` と `w × h × bytes_per_pixel` の不一致
- `file.u` と全パーツの `l` の合計の不一致
- クロップファイルの `f`、`w`、`h` とベースファイルの不一致

## 9. セキュリティ考慮事項

### 9.1 入力検証

実装は以下を検証しなければなりません（MUST）：
- ヘッダー形式と長さ
- JSONマニフェスト構造
- バッファオーバーフローを防ぐためのオフセットと長さ値
- 圧縮爆弾を検出するための圧縮率
- プールインデックスの範囲（配列境界外参照を防止）
- クロップフレームの参照連鎖の深さ（無限ループを防止）

### 9.2 リソース制限

実装は以下について合理的な制限を設けるべきです（SHOULD）：
- マニフェストサイズ
- ファイル数
- 画像サイズ
- 非圧縮データサイズ
- フレームプールサイズ
- アニメーション数
- アニメーションごとの `seq` 長さ、およびすべてのアニメーションの `seq` の合計要素数

## 10. 例

### 10.1 最小限のマスターファイル

```json
{
  "t": "eia",
  "c": "lz4",
  "v": 1,
  "f": ["Format:RGB24"],
  "e": ["note"],
  "i": [{
    "t": "m",
    "n": "0",
    "f": "RGB24",
    "w": 1920,
    "h": 1080,
    "s": 0,
    "l": 256000,
    "u": 6220800
  }]
}
```

データセクション: `$` の直後から 256000 バイトの LZ4圧縮データ。展開すると 6220800 バイト（= 1920×1080×3）の画像データ。

### 10.2 クロップファイルを含む例

マスターファイル（スライド0）とクロップファイル（スライド1）を含む例：

```json
{
  "t": "eia",
  "c": "lz4",
  "v": 1,
  "f": ["Format:RGB24"],
  "e": ["note"],
  "i": [
    {
      "t": "m",
      "n": "0",
      "f": "RGB24",
      "w": 1920,
      "h": 1080,
      "s": 0,
      "l": 256000,
      "u": 6220800
    },
    {
      "t": "c",
      "b": "0",
      "n": "1",
      "f": "RGB24",
      "w": 1920,
      "h": 1080,
      "s": 256000,
      "l": 5000,
      "u": 15000,
      "r": [
        {
          "x": 100,
          "y": 200,
          "w": 50,
          "h": 100,
          "s": 0,
          "l": 15000
        }
      ]
    }
  ]
}
```

データセクション:
- バイト 0〜255999: スライド0の圧縮データ（`s=0, l=256000`）
- バイト 256000〜260999: スライド1の圧縮データ（`s=256000, l=5000`）
  - LZ4展開で 15000 バイト（= 50×100×3）のバッファが得られる
  - パーツの `s=0` はこの展開バッファ先頭を指す

デコード結果: スライド0の画像に、展開バッファのデータを `(100, 200)` から `50×100` の範囲に上書きした画像がスライド1。

### 10.3 アニメーションコンテナを含む例

スライド0にアニメーション（`id: "intro"`）を配置する例：

```json
{
  "t": "eia",
  "c": "lz4",
  "v": 1,
  "f": [
    "Format:RGB24",
    "Feature:animation"
  ],
  "e": ["a"],
  "i": [
    {
      "t": "m",
      "n": "0",
      "f": "RGB24",
      "w": 1920,
      "h": 1080,
      "s": 0,
      "l": 256000,
      "u": 6220800,
      "e": {
        "a": [{"id": "intro", "x": 100, "y": 200, "w": 400, "h": 300}]
      }
    }
  ],
  "ac": {
    "pool": [
      {
        "t": "m",
        "f": "RGB24",
        "w": 400,
        "h": 300,
        "s": 256000,
        "l": 15000,
        "u": 360000
      },
      {
        "t": "c",
        "f": "RGB24",
        "w": 400,
        "h": 300,
        "b": 0,
        "s": 271000,
        "l": 24000,
        "u": 120000,
        "r": [
          {
            "x": 50,
            "y": 50,
            "w": 200,
            "h": 200,
            "s": 0,
            "l": 120000
          }
        ]
      }
    ],
    "anims": [
      {
        "id": "intro",
        "fps": 30,
        "seq": [0, 1, 0]
      }
    ]
  }
}
```

この例では：
- スライド0の拡張 `e.a` にアニメーション参照配列が格納されている
- `ac.pool[0]` がフレーム0（マスター）、`ac.pool[1]` がフレーム1（フレーム0のクロップ）
- `ac.anims[0].seq = [0, 1, 0]` で、フレーム0 → フレーム1 → フレーム0 の往復アニメーション
- フレーム0が2回参照されるが、プールデータは1つだけでデータ重複がない

## 付録B: `s` フィールドの座標系まとめ

EIA v1では `s` という名前のフィールドが複数の異なる座標系で使われます。混同に注意してください。

| フィールド | 単位 | 起点 | 値の例 |
|---|---|---|---|
| `EIAFileV1Master.s` | 圧縮済みバイト | `$`直後 | 0, 256000, ... |
| `EIAFileV1Cropped.s` | 圧縮済みバイト | `$`直後 | 256000, ... |
| `EIAFileV1CroppedPart.s` | 非圧縮バイト | そのファイルの展開バッファ先頭 | 0, 15000, ... |
| `EIAAnimFramePoolItemMaster.s` | 圧縮済みバイト | `$`直後 | 大きな値 |
| `EIAAnimFramePoolItemCropped.s` | 圧縮済みバイト | `$`直後 | 大きな値 |
| `EIAAnimFramePoolItemCropped.r[i].s` | 非圧縮バイト | そのフレームの展開バッファ先頭 | 0, ... |
